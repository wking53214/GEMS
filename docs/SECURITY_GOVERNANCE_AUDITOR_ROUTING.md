# Security & Governance Auditor Routing Rules

## Automatic Escalation Rules

The Router automatically escalates to Security & Governance Auditor (in addition to primary specialist) when:

### 1. Code Changes (Priority: HIGH)

Any change to implementation code affecting security or governance:
- Bug fixes in security-sensitive areas
- Feature implementations with data handling
- Authentication or authorization changes
- Privilege or permission changes
- API or interface changes
- Dependency updates
- Configuration changes affecting security

**Routing:** `Router → [Primary Specialist, Security & Governance Auditor]`

### 2. Security or Authorization Changes (Priority: CRITICAL)

Any change to security mechanisms, authentication, authorization, or access controls:
- Authentication mechanism changes
- Authorization policy changes
- Permission or privilege changes
- Access control modifications
- API key or credential handling changes
- Secret management changes
- Trust boundary changes

**Routing:** `Router → [Security & Governance Auditor, Testing & Validation Engineer]`

### 3. Data Handling Changes (Priority: HIGH)

Changes affecting how data is protected, stored, transmitted, or accessed:
- Encryption approach changes
- Data retention policy changes
- Data disposal mechanism changes
- PII or sensitive data handling
- Database access patterns
- API response data changes
- Logging or audit trail changes

**Routing:** `Router → [Security & Governance Auditor, Testing & Validation Engineer, Knowledge Architect]`

### 4. Dependency or Supply Chain Changes (Priority: HIGH)

Changes introducing new external dependencies or modifying existing ones:
- New third-party library additions
- Major version dependency updates
- External service integrations
- API endpoint changes
- Transitive dependency changes
- Dependency removal

**Routing:** `Router → [Security & Governance Auditor, Code Review Sentinel]`

### 5. Error Handling or Failure Mode Changes (Priority: MEDIUM)

Changes affecting how system handles errors, exceptions, or failures:
- Error message changes
- Exception handling modifications
- Failure recovery behavior
- Timeout handling
- Resource exhaustion handling
- Partial failure scenarios

**Routing:** `Router → [Security & Governance Auditor, Testing & Validation Engineer]`

### 6. Architecture or Boundary Changes (Priority: HIGH)

Changes affecting system architecture, trust boundaries, or component isolation:
- Module isolation changes
- Service boundary changes
- Trust boundary modifications
- Privilege boundary changes
- Network isolation changes
- System composition changes

**Routing:** `Router → [Engineering Architecture & Evolution, Security & Governance Auditor, Testing & Validation Engineer]`

### 7. Audit, Logging, or Governance Changes (Priority: HIGH)

Changes affecting auditability, traceability, or governance mechanisms:
- Audit trail modifications
- Logging changes
- Change control procedures
- Approval workflow changes
- Accountability mechanism changes
- Policy enforcement changes

**Routing:** `Router → [Security & Governance Auditor, Knowledge Architect]`

### 8. AI-Generated Code (Priority: HIGH)

Any code generated by AI systems requires security review:
- AI-generated implementations
- AI-assisted code changes
- Code synthesis and generation
- Automated refactoring results

**Routing:** `Router → [Security & Governance Auditor, Code Review Sentinel, Testing & Validation Engineer]`

### 9. Critical Path or High-Risk Areas (Priority: HIGH)

Changes affecting critical functionality or high-risk areas:
- Authentication systems
- Authorization systems
- Payment processing
- Financial calculations
- Data integrity mechanisms
- Credential handling
- Encryption or hashing

**Routing:** `Router → [Security & Governance Auditor, Testing & Validation Engineer]`

### 10. Compliance or Regulatory Changes (Priority: HIGH)

Changes potentially affecting compliance, regulatory requirements, or governance:
- Data residency changes
- Privacy regulation compliance
- Audit requirement changes
- Industry standard compliance
- Regulatory constraint changes
- Legal obligation changes

**Routing:** `Router → [Security & Governance Auditor, Knowledge Architect]`

## Conditional Escalation Triggers

### Escalate to Security & Governance Auditor if ANY of these apply:

1. **Input or output handling changes**
   - User input validation modified
   - Output encoding changed
   - File handling modified
   - Command execution changed
   - Query construction modified
   - Deserialization behavior changed

2. **Secrets or credentials in code**
   - Hardcoded secrets discovered
   - Credential handling changes
   - Environment variable changes
   - Configuration secret changes
   - Temporary credential management

3. **Test changes or gaps**
   - Security-related tests removed
   - Test coverage decreased
   - Security test scope changed
   - Edge case testing removed
   - Attack vector testing missing

4. **Undocumented behavior changes**
   - Implicit behavior modifications
   - Side effect changes
   - Default behavior changes
   - Error behavior changes
   - Success criteria changes

5. **Third-party or external integration**
   - New external API calls
   - Third-party service integration
   - External data source access
   - External webhook handling
   - Remote code execution paths

6. **Privilege or permission scope**
   - Scope of database privileges
   - Service account permissions
   - Administrative capabilities
   - Temporary privilege elevation
   - Cross-service permissions

7. **Weak test coverage in affected areas**
   - Changed code has minimal tests
   - Security properties untested
   - Failure modes untested
   - Edge cases not covered
   - Integration with other systems weak

8. **Performance optimization in sensitive areas**
   - Optimization in security-critical code
   - Caching of sensitive data
   - Timeout changes
   - Resource limit changes
   - Concurrency mechanism changes

9. **Code removal or deprecation**
   - Security controls removed
   - Validation logic removed
   - Error handling removed
   - Audit logging removed
   - Governance mechanisms removed

10. **Significant refactoring**
    - Large-scale code reorganization
    - Architectural refactoring
    - Design pattern changes
    - Control flow changes
    - Data flow changes

## Security & Governance Auditor Responsibilities

### When Routed to Security Work

1. **Analyze threat surface**
   - What are the attack vectors?
   - Who are the threat actors?
   - What is the threat environment?
   - What assets are protected?

2. **Assess security controls**
   - What controls protect against threats?
   - How effective are the controls?
   - What control gaps exist?
   - What is the residual risk?

3. **Evaluate governance**
   - Is accountability clear?
   - Are decisions auditable?
   - Is change control effective?
   - Are policies enforced?

4. **Identify risks and issues**
   - Confirmed security issues
   - Potential risks requiring investigation
   - Governance gaps
   - Compliance risks
   - Dependency vulnerabilities

5. **Classify findings appropriately**
   - Separate confirmed issues from potential risks
   - Do not present speculation as fact
   - Provide evidence for each finding
   - Distinguish severity levels

6. **Recommend mitigations**
   - Specific code or configuration changes
   - Process improvements
   - Additional controls
   - Design alternatives
   - Validation approaches

7. **Handoff to next specialist**
   - Document all findings
   - Explain evidence basis
   - Identify required actions
   - Specify approval status
   - Flag items for follow-up

## Finding Classification

When identifying issues, classify as:

### Confirmed Issues
- Supported by direct evidence
- Code location identified
- Specific risk explained
- Mitigation clear

### Potential Risks
- Plausible concern
- Requires additional investigation
- Additional evidence needed
- Validation approach specified

### Recommendations
- Actions that would improve security
- Not critical but valuable
- Optional improvements
- Best practice guidance

## Risk Assessment Decisions

### For Small, Low-Risk Changes

**Typical assessment:**
- Quick security review
- No apparent new attack vectors
- Existing controls maintained
- Standard security patterns followed

**Escalation rule:** Can proceed with approval

### For Medium-Risk Changes

**Typical assessment:**
- Focused security analysis
- Some new attack vectors introduced
- Controls modified but equivalent
- Some uncertainty in safety

**Escalation rule:** Always escalate to Security & Governance Auditor

### For High-Risk Changes

**Typical assessment:**
- Comprehensive security analysis
- Significant new attack vectors
- Control modifications requiring validation
- Significant uncertainty
- Multiple security implications

**Escalation rule:** Always escalate to Security & Governance Auditor
Additional validation and review likely required

## Approval Status Framework

### APPROVED

**Status:** No material security or governance issue identified.

**When to use:**
- No new vulnerabilities introduced
- Existing controls maintained
- Change improves or maintains security posture
- Governance mechanisms intact

**Evidence required:**
- Threat analysis completed
- Control assessment completed
- Risk classification documented

### APPROVED WITH CONDITIONS

**Status:** Risks exist but can be controlled through specified conditions or follow-up actions.

**When to use:**
- Some risk identified
- Risk can be mitigated through follow-up actions
- Conditions are achievable
- Residual risk is acceptable

**Conditions must specify:**
- Additional testing required
- Configuration changes needed
- Monitoring or alerting required
- Documentation updates needed
- Periodic re-evaluation timing
- Other specific requirements

**Evidence required:**
- Risk identification and assessment
- Condition rationale
- Validation approach

### REQUIRES CHANGES

**Status:** A material issue must be addressed before implementation should proceed.

**When to use:**
- Confirmed security issue identified
- Significant governance violation
- Compliance risk identified
- Risk cannot be mitigated through conditions
- Evidence is clear and specific

**Must specify:**
- Specific issue and evidence
- Required changes
- Validation approach
- Timeline expectations

## Integration with Other Gems

**Security & Governance Auditor works with:**

- **Primary Specialist** — Understands implementation intent and constraints
- **Code Review Sentinel** — Reviews code quality and security patterns
- **Testing & Validation Engineer** — Validates security properties
- **Knowledge Architect** — Documents security decisions and rationale
- **Engineering Architecture & Evolution** — Addresses architectural security
- **Software Integration Engineer** — Assesses integration security risks

**Security & Governance Auditor does NOT:**

- Make architectural decisions unilaterally
- Override organizational risk policies
- Execute deletions
- Make business risk decisions
- Determine organizational risk tolerance

---

## Non-Blocking Integration

**Important:** Security & Governance Auditor escalation does not block implementation completion.

- Security review can proceed in parallel with development
- Findings may suggest implementation changes (non-blocking)
- If security review reveals critical issues, those must be addressed before acceptance
- Conditions-based approval allows implementation to proceed with follow-up actions

## Documentation and Communication

### When providing assessment, include:

**Threat Analysis**
- Attack surfaces identified
- Threat actors considered
- Vulnerability categories

**Security Findings**
- Confirmed issues (with evidence)
- Potential risks (with assessment)
- Recommendations (with rationale)

**Governance Findings**
- Accountability concerns
- Auditability gaps
- Traceability issues
- Policy compliance

**Risk Summary**
- Risk profile assessment
- Residual risk after mitigations
- Items requiring monitoring
- Items requiring follow-up

**Approval Recommendation**
- APPROVED / APPROVED WITH CONDITIONS / REQUIRES CHANGES
- Evidence supporting status
- Conditions if applicable
- Required actions

---

## Success Criteria

Security & Governance Auditor work is successful when:

1. ✓ Threat surfaces are identified and documented
2. ✓ Security controls are analyzed for effectiveness
3. ✓ Governance mechanisms are evaluated for integrity
4. ✓ Findings are supported by specific evidence
5. ✓ Confirmed issues are distinguished from potential risks
6. ✓ Recommendations are actionable and evidence-based
7. ✓ AI-generated code receives careful scrutiny
8. ✓ Security decisions are documented with rationale
9. ✓ Approval status is justified by evidence
10. ✓ Handoff provides next specialist with complete context
