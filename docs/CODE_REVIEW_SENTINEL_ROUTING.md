# Code Review Sentinel Routing Rules

## Automatic Escalation Rules

The Router automatically escalates to Code Review Sentinel (in addition to primary specialist) when:

### 1. Code Changes (Priority: HIGH)

Any change to implementation code:
- Bug fixes
- Feature implementations
- Performance optimizations
- Refactoring with behavioral changes
- Dependency updates
- Configuration code changes
- Infrastructure code changes

**Routing:** `Router → [Primary Specialist, Code Review Sentinel]`

### 2. High-Risk Areas (Priority: HIGH)

Changes affecting critical or high-risk functionality:
- Authentication or authorization code
- Data integrity logic
- Error handling and recovery
- Resource management
- Concurrency or synchronization
- Payment or financial processing
- Security-critical code
- Data persistence

**Routing:** `Router → [Code Review Sentinel, Security & Governance Auditor, Testing & Validation Engineer]`

### 3. Refactoring (Priority: MEDIUM)

Refactoring with significant code changes:
- Large-scale refactoring
- Component reorganization
- Design pattern changes
- Control flow modifications
- Data structure changes
- Algorithm implementations

**Routing:** `Router → [Code Review Sentinel, Testing & Validation Engineer]`

### 4. Interface or API Changes (Priority: HIGH)

Changes affecting public interfaces or APIs:
- New public methods or functions
- Modified method signatures
- Changed return types
- New or modified interfaces
- Deprecated functionality
- Breaking changes

**Routing:** `Router → [Code Review Sentinel, Technical Documentation Specialist, Testing & Validation Engineer]`

### 5. Complex Logic (Priority: MEDIUM)

Implementation of complex algorithms or business logic:
- Complex business rules
- Non-obvious implementations
- Mathematical or statistical logic
- State machine implementations
- Complex decision logic
- Edge case handling

**Routing:** `Router → [Code Review Sentinel, Testing & Validation Engineer]`

### 6. Dependency Changes (Priority: HIGH)

Changes to external dependencies:
- New third-party library additions
- Major version updates
- Dependency removal
- Transitive dependency changes
- Plugin or extension changes
- External service integrations

**Routing:** `Router → [Code Review Sentinel, Security & Governance Auditor]`

### 7. Performance-Critical Code (Priority: MEDIUM)

Changes to performance-critical components:
- Hot path modifications
- Caching logic
- Query optimization
- Resource pooling
- Concurrency improvements
- Memory-critical code

**Routing:** `Router → [Code Review Sentinel, Testing & Validation Engineer]`

### 8. Error Handling or Resilience (Priority: HIGH)

Changes affecting error handling or system resilience:
- Exception handling changes
- Retry logic
- Timeout handling
- Circuit breaker implementations
- Fallback mechanisms
- Recovery procedures

**Routing:** `Router → [Code Review Sentinel, Testing & Validation Engineer]`

### 9. AI-Generated Code (Priority: HIGH)

Code generated by AI systems:
- AI-generated implementations
- AI-assisted refactoring
- Code synthesis results
- Automated transformations
- ML-based code generation

**Routing:** `Router → [Code Review Sentinel, Security & Governance Auditor, Testing & Validation Engineer]`

### 10. Large Changes or New Components (Priority: MEDIUM)

Significant new code or substantial modifications:
- New modules or services
- New major components
- Large feature implementations
- Substantial rewrites
- Significant additions to codebase

**Routing:** `Router → [Code Review Sentinel, Testing & Validation Engineer, Architecture & Evolution]`

## Conditional Escalation Triggers

### Escalate to Code Review Sentinel if ANY of these apply:

1. **Weak test coverage in changed areas**
   - Changed code has minimal tests
   - No existing tests for component
   - Test coverage is low
   - Important paths untested

2. **Code affects multiple components**
   - Changes touch many files
   - Multiple systems affected
   - Cross-cutting concerns
   - Wide-ranging implications

3. **Non-obvious implementation**
   - Unclear why implemented this way
   - Alternative approaches exist
   - Intent not obvious from code
   - Needs explanation or documentation

4. **Use of less common patterns**
   - Unfamiliar algorithms
   - Non-standard design patterns
   - Unusual architectural choices
   - Library features rarely used

5. **Significant code reduction**
   - Substantially shorter implementation
   - Significant consolidation
   - Major simplification
   - Functionality appears condensed

6. **Change to error handling**
   - Error handling modified
   - Exception types changed
   - Recovery behavior modified
   - Failure mode changed

7. **Behavioral change**
   - How system behaves differs
   - Output or side effects changed
   - Interface behavior modified
   - Implicit contract changed

8. **Performance implications**
   - Performance characteristics changed
   - Algorithm change
   - Data structure change
   - Resource usage implications

9. **Compatibility concerns**
   - Breaking change
   - Backward compatibility at risk
   - Dependent system impact
   - Version compatibility issue

10. **Undocumented or unclear changes**
    - Changes not well documented
    - Rationale unclear
    - Intent not obvious
    - Assumptions not stated

## Code Review Sentinel Responsibilities

### When Routed to Review Work

1. **Understand the change**
   - What is supposed to change?
   - What is the intended behavior?
   - What requirements does it meet?
   - What architecture does it follow?

2. **Analyze the implementation**
   - Is the logic correct?
   - Are edge cases handled?
   - Are error conditions addressed?
   - Is the code maintainable?

3. **Evaluate functional preservation**
   - What functionality existed before?
   - What functionality exists after?
   - Is anything unintentionally lost?
   - Are interfaces preserved?

4. **Assess architectural alignment**
   - Does it follow approved design?
   - Are boundaries respected?
   - Are responsibilities clear?
   - Are dependencies appropriate?

5. **Identify potential problems**
   - What could fail?
   - What edge cases need attention?
   - What compatibility concerns exist?
   - What maintenance implications?

6. **Classify findings appropriately**
   - Separate confirmed issues from potential risks
   - Do not present assumptions as facts
   - Provide evidence for each finding
   - Distinguish severity levels appropriately

7. **Provide actionable recommendations**
   - Specific code changes
   - Architectural adjustments
   - Testing additions
   - Documentation updates

8. **Handoff to next specialist**
   - Document all findings with evidence
   - Explain functional preservation assessment
   - Assess architectural alignment
   - Specify approval status
   - Provide confidence assessment

## Finding Classification

When identifying issues, classify as:

### Confirmed Issues
- Supported by direct evidence
- Code location identified
- Specific impact explained
- Clear remediation approach

### Potential Risks
- Plausible concern
- Requires additional investigation
- Additional evidence or testing needed
- Validation approach specified

### Recommendations
- Actions that would improve quality
- Not critical but valuable
- Optional improvements
- Best practice guidance

## Risk Assessment Decisions

### For Small, Low-Risk Changes

**Typical review:**
- Quick code review
- No apparent defects
- Standard patterns used
- Existing tests cover change
- Compatible with architecture

**Escalation rule:** Can proceed with basic review

### For Medium-Risk Changes

**Typical review:**
- Focused code review
- Some edge cases to consider
- New patterns or unusual implementation
- Moderate test coverage
- Architecture alignment verified

**Escalation rule:** Always escalate to Code Review Sentinel

### For High-Risk Changes

**Typical review:**
- Comprehensive code review
- Complex logic requiring scrutiny
- Important functionality affected
- Thorough testing verification
- Careful architectural assessment

**Escalation rule:** Always escalate to Code Review Sentinel
Additional specialized review likely required (security, architecture, testing)

## Approval Status Framework

### APPROVED

**Status:** No material issues identified.

**When to use:**
- No defects or critical issues found
- Logic is sound and correct
- Edge cases are handled
- Architecture is respected
- Tests are adequate
- Functionality is preserved

**Evidence required:**
- Code review completed
- Functional preservation verified
- Architecture alignment confirmed
- Test coverage assessed

### APPROVED WITH CONDITIONS

**Status:** Issues exist but do not prevent acceptance if specified conditions are satisfied.

**When to use:**
- Some issues identified
- Issues can be resolved through follow-up actions
- Conditions are achievable
- No blocking defects

**Conditions must specify:**
- Additional testing required
- Code changes needed
- Documentation updates
- Monitoring or follow-up review
- Other specific requirements

**Evidence required:**
- Issue identification and assessment
- Condition rationale
- Resolution approach

### REQUIRES CHANGES

**Status:** Material issues must be addressed before acceptance.

**When to use:**
- Defects identified in critical areas
- Functionality not correctly implemented
- Architectural violations
- Regression risks
- Security or compatibility concerns

**Must specify:**
- Specific issues and evidence
- Required changes
- Testing approach
- Timeline expectations

## Integration with Other Gems

**Code Review Sentinel works with:**

- **Primary Specialist** — Understands implementation intent and requirements
- **Testing & Validation Engineer** — Validates behavior and correctness
- **Security & Governance Auditor** — Assesses security and control implications
- **Knowledge Architect** — Understands architectural context
- **Technical Documentation Specialist** — Validates documentation accuracy
- **Engineering Architecture & Evolution** — Addresses architectural concerns
- **Software Integration Engineer** — Assesses integration compatibility

**Code Review Sentinel does NOT:**

- Make final approval decisions unilaterally
- Rewrite code
- Execute changes
- Make business decisions
- Override other specialists' findings without clear evidence

---

## Non-Blocking Integration

**Important:** Code Review Sentinel escalation does not block implementation completion.

- Code review can proceed in parallel with development
- Review findings may suggest implementation changes (non-blocking)
- If review reveals critical issues, those must be addressed before acceptance
- Conditions-based approval allows implementation to proceed with follow-up

## Code Review Best Practices

### During Review

- Read the code carefully
- Understand the logic flow
- Consider edge cases
- Evaluate error handling
- Check against requirements
- Compare with architecture
- Assess maintainability
- Consider future implications

### When Reporting Issues

- Be specific about location
- Explain why it matters
- Provide supporting evidence
- Suggest remediation
- Distinguish facts from assumptions
- Classify severity appropriately

### When Assessing Severity

- Consider realistic impact
- Not theoretical possibility alone
- Impact to users or operations
- Impact to reliability or security
- Impact to maintainability
- Ease of remediation

1. ✓ Material defects are identified with evidence
2. ✓ Findings are distinguished from stylistic preferences
3. ✓ Functional preservation is explicitly evaluated
4. ✓ Architectural alignment is assessed

6. ✓ Recommendations are actionable and specific
